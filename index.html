Two takes on atomic styling

TailwindvsStyleX

Two tools that agree the output should be atomic CSS — and disagree about almost everything else. How each one works, where they genuinely split, and how to read both fluently, wherever you're coming from.

Same jobs, two owners

Both cover the entire styling surface. They just hand each job to a different mechanism — and usually at a different moment: strings resolved by a scanner vs typed objects resolved by a compiler.

The course

The six splits

Where the two genuinely diverge. Not a scoreboard — six design decisions, each made deliberately, each with a real cost on the other side.

01

Strings ↔ typed data

Styling as terse text living in the markup, or as values the type system can see, pass, and refactor.

02

Stylesheet ↔ call site

When two rules touch one property, precedence is decided by the framework's stylesheet — or by argument order where you wrote it.

03

Naming ↔ imports

Tokens reached by convention (bg-brand-500), or reached through the module graph (color.brand500).

04

Open ↔ negotiated

className lets any caller restyle anything. StyleX lets a component type exactly what may be overridden.

05

Portability ↔ depth

Works anywhere HTML is produced, or buys deep integration by living inside the JS/JSX toolchain.

06

Vocabulary ↔ CSS

Learn a dictionary once and type less forever, or write CSS property names and learn nothing new.

Tailwind in the wild: the shadcn stack

        outline: "border border-input bg-background hover:bg-accent",
      },

function Button({ className, variant, size, asChild = false, ...props }) {
  const Comp = asChild ? Slot : "button";
  return (
    <Comp
      className={cn(buttonVariants({ variant, size }), className)}
      {...props} />

Tailwind rarely arrives alone. Four libraries share the work in the stack most people actually meet it in:

  • Tailwind — the vocabulary and the compiler behind it
  • cva — assembles variant class strings
  • clsx + tailwind-merge — cn(): compose strings, then delete the conflicts
  • Radix / Base UI — behavior, focus, a11y; asChild for composition
Only the first three are the styling half — that's this deck.
The behavior half is a separate axis with its own deck.
Ch 1 · Meet Tailwind

What Tailwind actually is

Worth stating precisely, because the popular description ("inline styles with extra steps") is wrong, and the accurate one explains both tools at once.

  • It's a compiler: it scans source files for known class names and emits only those rules.
  • One class ≈ one declaration. p-4 is padding: 1rem. The output is atomic CSS.
  • Order inside the class string means nothing — precedence lives in the stylesheet, fixed by the framework.
  • Hence tailwind-merge: a runtime re-encoding of the taxonomy, purely to resolve conflicts.
  • v4 moved config into CSS (@theme → custom properties) and shipped a much faster engine.
what you typed
<div class="p-4 text-sm font-medium">
what shipped
.p-4 { padding: 1rem; }
.text-sm { font-size: .875rem; line-height: 1.25rem; }
.font-medium { font-weight: 500; }
Atomic, compiled, constrained. All three words also describe StyleX's output — which is exactly why the interesting differences are all in the authoring model, not the CSS.
Ch 2 · Meet StyleX

What StyleX is

  • CSS-in-JS with a compiler. Style objects leave your bundle at build time and become one static .css file.
  • The output is atomic classes — the same trick Tailwind plays, generated instead of memorized.
  • A tiny runtime, stylex.props(), merges class lists with one rule: the last style wins.
  • Typed end to end — properties, values, tokens, and what a component lets you override.
  • Built by Meta; styles facebook.com, instagram.com, WhatsApp Web, and Threads.
the elevator pitch

Tailwind's output model
+ TypeScript's authoring model

Modern surface assumed here (≈ v0.19+): conditions-as-values, defineConsts, derived variables.
Ch 2 · Meet StyleX

The same pill, twice

tailwind
export function Pill({ children }) {
  return (
    <span className="inline-flex items-center gap-1
      rounded-full bg-sky-100 px-3 py-1
      text-sm font-medium text-sky-700">
      {children}
    </span>
  );
}
stylex
import * as stylex from '@stylexjs/stylex';

const styles = stylex.create({
  pill: {
    display: 'inline-flex', alignItems: 'center', gap: 4,
    borderRadius: 999, backgroundColor: '#e0f2fe',
    paddingInline: 12, paddingBlock: 4,
    fontSize: 14, fontWeight: 500, color: '#0369a1',
  },
});

export function Pill({ children }) {
  return <span {...stylex.props(styles.pill)}>{children}</span>;
}
The trade in one screen: one is dramatically shorter and needs no import; the other names every property in full, and every one of those names is checked. Same rendered pill, same atomic CSS underneath.

Ch 2 · Meet StyleX

Atomic CSS: the shared premise

  • Both tools emit each unique declaration once, ever. Ten components using display: flex share one rule.
  • CSS grows with the vocabulary (≈ logarithmic), not with component count (linear).
  • Tailwind reaches it with a fixed dictionary you learn; StyleX generates it from what you wrote.
  • This is the agreement. Everything else in this deck sits above the line — in how you author.
Two tools, one output model, opposite authoring philosophies. That's the whole comparison in a sentence.

Ch 3 · Split 1 of 6

Strings ↔ typed data

Tailwind

Styling you can read in the markup

  • The whole look of an element fits on one line, next to the element.
  • No import, no naming ceremony — and naming things is the expensive part of CSS.
  • The editor plugin gives completion and hover-previews of the real CSS.
  • Class strings are greppable from any language, including templates.
Costs: the compiler cannot see "felx" — a typo renders fine and ships fine. Strings do not participate in rename-refactors, and class names built at runtime break scanning entirely.
StyleX

Styling the type system can see

  • Properties and values are checked: a typo is a build error, not a silent no-op.
  • Rename-symbol, find-all-references, and unused-style lint all work.
  • Styles are values — pass them as props, export them, map over them.
  • Deleting a component provably deletes its CSS.
Costs: verbosity. An import plus a create() block before you style anything, and the styles now sit away from the markup you are reading.
Both are compiled and both are constrained. The question is whether you want the constraint enforced by a dictionary of names or by a type checker.
Ch 3 · Split 2 of 6

Stylesheet order ↔ call-site order

Tailwind

Precedence is global, and not your problem

  • You never reason about specificity — the framework fixed the order for you.
  • Two utilities on one element resolve identically in every file, forever.
  • Great for a team: nobody can invent a novel precedence scheme.
Costs: when class strings merge — a base plus a caller override — the fix is tailwind-merge: a runtime library that re-encodes the whole taxonomy to delete conflicts. Real bundle and CPU cost, and it must track every new utility.
StyleX

Precedence is local, and explicit

  • stylex.props(a, b) — b wins, per property. That is the entire rule.
  • No specificity, no !important, no merge library in the bundle.
  • A component decides once, in readable source, whether callers can override it.
  • Falsy arguments are skipped, so conditionals are plain &&.
Costs: only StyleX styles participate. A raw className arriving from outside does not merge — it just lands beside yours, back in cascade-land.
Same problem — “who wins?” — answered at opposite ends: a stylesheet you never see vs the argument list you just typed.
Ch 3 · Split 3 of 6

Tokens by naming ↔ tokens by import

Tailwind

@theme in CSS, reachable from anywhere

  • Tokens live in a stylesheet, so any file type can use them — templates, emails, CMS content.
  • Designers and non-JS engineers can read and edit the source of truth.
  • v4 compiles @theme straight to CSS custom properties.
Costs: resolution is by convention. Nothing catches a token that no longer exists beyond the class silently not applying, and renaming one is a find-and-replace across strings in every language in the repo.
StyleX

defineVars() in the module graph

  • Tokens are typed imports: rename them, deprecate them, count their references.
  • Derived tokens compile to real var() chains, so a theme override cascades through the graph.
  • Unused tokens and bad references surface at build time.
Costs: reachable only from JS/TS modules, and *.stylex.ts files are a compiler contract — they may export nothing but token groups.
The compiled output is nearly identical: custom properties on :root. What differs is whether your tooling understands the token graph.
Ch 3 · Split 4 of 6

Open className ↔ negotiated contracts

Tailwind

Anyone can restyle anything

  • The fastest escape hatch in existence: add a class, ship the fix.
  • No API design meeting to add one margin at one call site.
  • It is precisely why the copy-and-own component model works so well.
Costs: className?: string is an unbounded API. Every consumer override silently forks a design decision, nothing records that it happened, and you cannot change the component later without breaking overrides you never knew about.
StyleX

The component types what may change

  • Open: style?: StyleXStyles — anything goes.
  • Scoped: StyleXStyles<{ color?: string }> — only these properties.
  • Closed: Omit<…, 'className' | 'style'> — the system decides.
  • Overrides become a typed negotiation, visible in review.
Costs: rigidity. The legitimate one-off now needs an upstream change or a fork, and someone has to design the contract before anyone can use it.
Design systems tend to want the contract; product teams under deadline tend to want the hatch. Most codebases need both, at different layers.
Ch 3 · Split 5 of 6

Portability ↔ integration depth

Tailwind

Works anywhere HTML is produced

  • Rails, Django, Laravel, Go templates, PHP, Astro, Svelte, Vue, plain .html.
  • Class names are just strings — any language can emit them.
  • A CDN script tag styles a page with no build step at all.
  • Rewrite React → Svelte and the markup keeps its styling.
Costs: the flip side of strings is everything in split 1 — no type checking, and tooling that can only guess at your intent.
StyleX

Lives inside the JS module graph

  • A Babel/bundler step is required, and styles must be statically analyzable.
  • In exchange the compiler can do things a scanner cannot: typed override contracts, token graphs, per-property merging, provable dead-style elimination.
  • Tokens, themes, and styles are ordinary module exports.
Costs: if part of your app renders HTML from a language that is not JavaScript, StyleX simply cannot style it. Server-rendered JS frameworks are fine; Rails views are not.
The least negotiable split on this list. It is a hard architectural fact about your stack, not a preference — check it first.
Ch 3 · Split 6 of 6

A vocabulary ↔ plain CSS

Tailwind

Learn a dictionary, type far less

  • p-4 flex gap-2 beats fourteen words of object literal, every time.
  • The default scale is a constraint: spacing and color come from the theme unless you fight it.
  • Arbitrary values need brackets — w-[137px] — so one-offs look like one-offs.
Costs: you must learn and retain the mapping; CSS knowledge does not transfer one-to-one, rarer properties fall back to bracket syntax, and a CSS-fluent new hire is still a beginner on day one.
StyleX

It is just CSS, in camelCase

  • Nothing new to learn: paddingInline, gridTemplateColumns, @media.
  • Knowledge transfers both directions — into the codebase and back out.
  • Any CSS value is legal; no escape syntax for width: 137.
  • Escape hatches stay explicit: dynamic styles, local create(), or a plain CSS file.
Costs: no constraint comes for free — nothing stops padding: 13. Tokens are the pit of success only if the team actually defines them. And static analysis forbids descendant selectors, runtime string styles, and !important.
Tailwind constrains by making the right thing shortest. StyleX constrains by making everything typed, then trusting your tokens. Different theories of how humans behave under deadline.

Layout & spacing

tailwind
<div class="flex items-center justify-between gap-3
            rounded-xl border border-zinc-800 p-4">
stylex
const styles = stylex.create({
  card: {
    display: 'flex',
    alignItems: 'center',
    justifyContent: 'space-between',
    gap: 12,
    borderRadius: 12,
    borderWidth: 1,
    borderStyle: 'solid',
    borderColor: '#27272a',
    padding: 16,
  },
});
  • Single-value shorthands are fine (padding: 16). The lint blocks multi-value ones (padding: '12px 16px') — longhands keep merging deterministic.
  • Prefer logical properties: paddingInline, marginBlock, borderStartStartRadius — RTL support falls out for free.
  • No scale to memorize: gap: 12 is 12px. Your design system's scale arrives as tokens instead.

States: variants vs conditions

tailwind

link: {
  color: {

idiom b · render-prop states (headless components)

    isHovered && styles.hovered,

</Button>
  • Note the condition lives inside the property — so states merge per property, like everything else.
  • Headless libraries normalize messy platform states (touch vs mouse, focus-visible quirks) into clean booleans — style the semantic state, not the raw selector.

Ch 4 · Side by side

Variants: a table lookup, either way

button.tsx · the style tables
// (a `base` create() with shared flex/radius styles is elided)

const variants = stylex.create({
  primary: {
    backgroundColor: {
      default: color.primary,
      ':hover': color.primaryHover,
    },
    color: color.onPrimary,
  },
  outline: {
    backgroundColor: { default: 'transparent' },
    borderWidth: 1, borderStyle: 'solid',
    borderColor: color.border,
  },
});

const sizes = stylex.create({
  md: { height: 36, paddingInline: 16 },
  lg: { height: 40, paddingInline: 24 },
});
…and the component
type Props = {
  variant?: keyof typeof variants;  // ← the union type is free
  size?: keyof typeof sizes;
} & Omit<React.ComponentProps<'button'>, 'className' | 'style'>;

export function Button(
  { variant = 'primary', size = 'md', ...props }: Props
) {
  return <button {...props}
    {...stylex.props(base.root, variants[variant], sizes[size])} />;
}
  • Both are lookup tables. cva returns a class string; StyleX returns a style object — variants[variant].
  • compoundVariants → plain booleans:
    variant === 'outline' && size === 'md' && styles.tweak
  • keyof typeof keeps props and styles in lockstep — add a variant, the union updates itself.
  • No config DSL. It's data and functions all the way down.

Styles across component boundaries

  children: React.ReactNode;

the remaining 10% of your day
const pulse = stylex.keyframes({
  '0%':   { opacity: 0.4 },
  '100%': { opacity: 1 },

const styles = stylex.create({

  • Pseudo-elements are keys on the owner's style: '::before', '::placeholder'…

  • Dynamic styles are the sanctioned runtime hatch: the class stays static; only a CSS variable changes per render.

Ch 5 · Toolchain & ecosystem

Adoption & pedigree

The least technical slide here, and often the most decisive one.

Tailwind CSS · v4.3 (May 2026)

The default answer

  • By Tailwind Labs; a decade old, 1.0 long since passed, shipping steadily (v4.1 masks & text shadows, v4.2 webpack plugin, v4.3 scrollbar utilities).
  • An enormous ecosystem: paid template libraries, thousands of blog posts, every UI kit, every LLM's default output.
  • Any new hire has probably already used it.
Watch for: gravity. Hard to argue against, easy to end up with by default rather than by decision.
StyleX · v0.19

The considered answer

  • By Meta; open-sourced Dec 2023. Runs facebook.com, instagram.com, WhatsApp Web and Threads — proof it scales further than your app will.
  • Active: v0.19 added @stylexjs/atoms for inline atomic styles, and there is a public v1.0 roadmap.
  • Adopted mostly by teams building a design system rather than an app.
Watch for: still 0.x, with a far smaller community. Fewer answers online, fewer ready-made components, more decisions you make yourself.
Honest framing: one is a safe default with a ceiling on rigor; the other is a rigorous bet with a smaller safety net.
Ch 5 · Toolchain & ecosystem

Wiring & day-to-day DX

tailwind v4 · two lines
// vite.config.ts
import tailwindcss from '@tailwindcss/vite';
export default defineConfig({ plugins: [tailwindcss()] });

// app.css
@import "tailwindcss";
  • Setup is minutes; official plugins for Vite, PostCSS and webpack.
  • IntelliSense extension is the DX story: completion, hover-preview, conflict warnings.
  • Tailwind Play — share a reproduction in a URL, no install.
stylex · three moving parts
// vite.config.ts — babel transforms
plugins: [react({ babel: { plugins: [
  ['@stylexjs/babel-plugin', { dev: mode === 'development',
    unstable_moduleResolution: { type: 'commonJS' } }],
] } })]
// + @stylexjs/postcss-plugin  → extracts one static stylex.css
// + @stylexjs/eslint-plugin   → valid-styles, valid-shorthands,
//                               no-unused, sort-keys
  • More setup, and it is build-coupled — no zero-config playground.
  • TypeScript is the IntelliSense — no editor extension to install.
  • dev: true keeps readable devtools names: Button__styles.root.
A fair summary: Tailwind optimises the first ten minutes, StyleX optimises the ten-thousandth commit. Which matters more is a real question about your project, not a rhetorical one.
Ch 6 · Verdicts

Tradeoffs, both directions

Every comparison that only lists one side's downsides is marketing. Here is what you actually give up, whichever way you go.

Leaving Tailwind, you will miss
  • Raw speed. Three words of class beat a twelve-line object at 5pm.
  • The ecosystem. Templates, UI kits, Stack Overflow, and every AI model's default output.
  • Reach. Styling markdown, CMS prose, emails, and non-JS templates.
  • Play. A shareable repro in a URL with nothing installed.
Leaving StyleX, you will miss
  • The type checker. Typos and bad values stop being a runtime surprise.
  • Deterministic merging with no merge library in the bundle.
  • Typed contracts. Knowing exactly what callers may restyle.
  • Refactorability. Rename a token, find every use, delete dead styles with proof.
Notice these lists are not opposites — they are different kinds of good. Speed and reach on one side, guarantees and refactorability on the other.
Ch 6 · Verdicts

Day-one gotchas

The things that trip people up in week one, in whichever direction they are travelling.

First week in StyleX
  • Multi-value shorthands are rejected: write marginBlock / marginInline, not margin: '8px 16px'.
  • You cannot style children. No .card:hover .icon — style the owner, pass state down.
  • create() lives at module top level with static keys. No factories.
  • Numbers become px, except unitless properties (lineHeight, opacity, zIndex).
  • Conditionals are cond && styles.x arguments — never assembled strings.
First week in Tailwind
  • Class names must appear whole in the source. bg-${c}-500 is invisible to the scanner — map to full class strings.
  • String order does nothing. To override reliably you need tailwind-merge.
  • Arbitrary values need brackets: w-[137px], bg-[#0b0e17].
  • v4 config is CSS-first (@theme) — most tutorials still show tailwind.config.js.
  • Install the Prettier sort plugin on day one, or class strings become unreadable.
Ch 6 · Verdicts

So: which one?

Choose Tailwind when
  • Any of your HTML comes from a non-JS template. This alone decides it.
  • Speed to ship dominates: prototype, marketing site, small team, startup.
  • The team is already fluent — and you are hiring for that fluency.
  • You lean on templates, UI kits, or AI codegen to move fast.
  • You want styling that outlives your current framework choice.
Choose StyleX when
  • You are building a design system consumed by many apps, not one app.
  • You need to stop silent forks — typed contracts over open className.
  • Large, long-lived React codebase that gets refactored repeatedly.
  • Multi-brand or nested theming needs to be a first-class value.
  • The team prefers compile-time guarantees over terseness.
And if it is a toss-up — an ordinary React product app with no design-system ambitions — it genuinely does not matter much. Pick the one your team already reads fluently, and spend the saved argument on tokens and accessibility instead.
