The course

The six mental shifts

This is the whole course in one slide. Each shift gets its own deep-dive in chapter 3.

01

Strings → data

Styles become typed values you can pass, inspect, lint, and refactor like any other code.

02

Cascade → call-site order

No specificity, no tailwind-merge. The last style listed wins — per property, always.

03

Config → modules

Design tokens are imports that travel the module graph, not naming conventions in a config file.

04

Open className → contracts

Components decide what callers may restyle — a few properties, everything, or nothing at all.

05

Copy → consume

From forking registry code into your repo to importing versioned components you help evolve.

06

Freedom → visible constraints

One-offs don't disappear — they become explicit escape hatches that show up in review.

Ch 1 · Where you're coming from

Anatomy of a shadcn component

button.tsx · from the registry
const buttonVariants = cva(
  "inline-flex items-center justify-center gap-2 rounded-md text-sm " +
    "font-medium transition-colors focus-visible:ring-2 disabled:opacity-50",
  {
    variants: {
      variant: {
        default: "bg-primary text-primary-foreground hover:bg-primary/90",
        outline: "border border-input bg-background hover:bg-accent",
      },
      size: { default: "h-9 px-4 py-2", sm: "h-8 px-3", lg: "h-10 px-6" },
    },
    defaultVariants: { variant: "default", size: "default" },
  }
);

function Button({ className, variant, size, asChild = false, ...props }) {
  const Comp = asChild ? Slot : "button";
  return (
    <Comp
      className={cn(buttonVariants({ variant, size }), className)}
      {...props} />
  );
}
  • Tailwind — the vocabulary and the compiler behind it
  • cva — assembles variant class strings
  • clsx + tailwind-merge — cn(): compose strings, then delete the conflicts
  • Radix — behavior, focus, a11y; asChild/Slot for composition
None of these four survive the move.
Every job they do still exists on the other side.
Ch 1 · Where you're coming from

What Tailwind actually is

Understanding your current tool precisely makes the new one obvious.

  • It's already a compiler: it scans source files for known class names and emits only those rules.
  • One class ≈ one declaration. p-4 is padding: 1rem. You've been writing atomic CSS by hand.
  • Order in your class string means nothing — precedence belongs to the stylesheet, fixed by the framework. "p-2 p-4" is not a choice you made.
  • That's why tailwind-merge exists: a runtime re-encoding of Tailwind's whole taxonomy, just to delete conflicts.
  • v4 made config CSS-first: @theme → CSS custom properties.
what you typed
<div class="p-4 text-sm font-medium">
what shipped
.p-4 { padding: 1rem; }
.text-sm { font-size: .875rem; line-height: 1.25rem; }
.font-medium { font-weight: 500; }
Hold that thought: atomic, compiled, constrained. You already bought the model — what changes is the authoring format.
Ch 2 · How StyleX works

What StyleX is

  • CSS-in-JS with a compiler. Style objects leave your bundle at build time and become one static .css file.
  • The output is atomic classes — the same trick Tailwind plays, generated instead of memorized.
  • A tiny runtime, stylex.props(), merges class lists with one rule: the last style wins.
  • Typed end to end — properties, values, tokens, and what a component lets you override.
  • Built by Meta; styles facebook.com, instagram.com, WhatsApp Web, and Threads.
the elevator pitch

Tailwind's output model
+ TypeScript's authoring model

Modern surface assumed here (≈ v0.19+): conditions-as-values, defineConsts, derived variables.
Ch 2 · How StyleX works

Hello, StyleX

before · tailwind
export function Pill({ children }) {
  return (
    <span className="inline-flex items-center gap-1
      rounded-full bg-sky-100 px-3 py-1
      text-sm font-medium text-sky-700">
      {children}
    </span>
  );
}
after · stylex
import * as stylex from '@stylexjs/stylex';

const styles = stylex.create({
  pill: {
    display: 'inline-flex', alignItems: 'center', gap: 4,
    borderRadius: 999, backgroundColor: '#e0f2fe',
    paddingInline: 12, paddingBlock: 4,
    fontSize: 14, fontWeight: 500, color: '#0369a1',
  },
});

export function Pill({ children }) {
  return <span {...stylex.props(styles.pill)}>{children}</span>;
}
Three things to notice: plain numbers become px (unitless props like lineHeight, opacity, fontWeight stay unitless) · camelCase, but standard CSS names — no dictionary · stylex.props() returns { className, style } and you spread it.

Ch 2 · How StyleX works

Atomic CSS: the math you already bought

  • Every unique declaration is emitted once, ever. Ten components using display: flex share one rule.
  • CSS grows with your vocabulary (≈ logarithmic), not your component count (linear).
  • This curve is how Meta ships one small static stylesheet for all of facebook.com.
  • Tailwind users already live on this curve. StyleX keeps the curve — and deletes the dictionary.
The plot twist of this course: you're not switching paradigms — you're switching notations for the same paradigm.

Ch 3 · Shift 1 of 6

Class strings → typed data

  • Autocomplete on every property and value — it's just TypeScript.
  • Find-all-references and rename-symbol work on styles and tokens.
  • stylex/no-unused flags dead styles; deleting a component deletes its CSS.
  • Styles are values: pass them as props, export them, map over them, test them.
  • The vocabulary is CSS itself — your knowledge transfers in and out.
tailwind · a typo is silence
<div className="felx items-center" />
// renders fine. ships fine. just… isn't flex.
stylex · a typo is a build error
const styles = stylex.create({
  row: { dsplay: 'flex' },
  //     ~~~~~~ TS error + stylex/valid-styles:
  //     unknown property 'dsplay'
});
Ch 3 · Shift 2 of 6

The cascade → call-site order

tailwind
<div className={cn("p-2 text-sm", isCard && "p-4")} />

// who wins? whatever tailwind-merge decides —
// p-4, because the library deletes p-2 for you.
// without cn(): the stylesheet's order decides.
// either way: not your call site.
stylex
<div {...stylex.props(styles.base, isCard && styles.card)} />

// styles.card wins — it's listed later.
// that's the entire rule.
// falsy values are skipped, so conditionals
// are plain && and ternaries.
  • No specificity scores, no !important, no source-order archaeology — deterministic, per property.
  • Possible because the compiler knows exactly which property each atomic class controls.
  • Retire the muscle memory: cn(), clsx, tailwind-merge have no equivalent because the problem is gone.
Ch 3 · Shift 3 of 6

Theme config → token modules

tailwind v4 · css-first config
@import "tailwindcss";

@theme {
  --color-brand-500: oklch(0.62 0.21 260);
  --spacing-18: 4.5rem;
}

/* usage: class="bg-brand-500 p-18"
   — resolved by naming convention */
tokens.stylex.ts · the suffix is a compiler contract
import * as stylex from '@stylexjs/stylex';

export const color = stylex.defineVars({
  brand500: 'oklch(0.62 0.21 260)',
  // newer stylex: "derived" tokens compile to
  // var() chains, so theme overrides cascade
});

// elsewhere — a typed import, not a convention:
import { color } from './tokens.stylex';
//   backgroundColor: color.brand500
Tokens travel the module graph: rename them, deprecate them, count their references — like any code. The compiled output is still a real CSS custom property on :root.
Ch 3 · Shift 4 of 6

Open className → styling contracts

three postures a component can take
// 1 · open — the caller may restyle anything
type Open = { style?: stylex.StyleXStyles };

// 2 · scoped — only these properties may change
type Scoped = {
  style?: stylex.StyleXStyles<{ color?: string; marginTop?: number }>;
};
<Text style={styles.brand} />   // ✅ recolors text
<Text style={styles.padded} />  // ❌ type error: padding isn't in the contract

// 3 · closed — the design system decides, full stop
type Closed = Omit<ComponentProps<'button'>, 'className' | 'style'>;
  • className?: string was an unbounded API — every consumer style silently forked your design decisions.
  • StyleX turns restyling into a typed negotiation.
  • Design systems typically ship closed or scoped components, with tokens & themes as the sanctioned customization path.
  • Omit<…, 'className' | 'style'> feels harsh for a week. Then it feels like a seatbelt.
Ch 3 · Shift 5 of 6

Copy the code → consume the package

shadcn's bet

The code lives in your repo

Infinite freedom, zero upgrade path — every edit is a fork you now maintain. A brilliant trade for a product that wants a head start and full ownership.

design system's bet

Components are versioned dependencies

You file issues, contribute upstream, and upgrade via changelog. Consistency across a fleet of apps and teams is the feature.

  • Day to day: you read Storybook and docs instead of source you own.
  • Extension points are props, tokens, themes — not editing the JSX.
  • “I'll just tweak it” becomes a small upstream PR. Slower once; faster every time after.
Ch 3 · Shift 6 of 6

One-off freedom → visible constraints

  • No string class names, no runtime style injection, no descendant selectors — everything must be statically analyzable.
  • Arbitrary values need no brackets: any CSS value is legal. What's constrained is where styles come from, not what they say.
  • Tokens become the pit of success — they're the thing that autocompletes.
  • You still have one-offs. They're just explicit, so review can see them.

The escape-hatch ladder

  • 1 · dynamic style function — runtime numbers become CSS vars (progress %, cursor positions)
  • 2 · local stylex.create in app code — one-offs are normal: colocated, typed, deletable
  • 3 · a plain .css file — resets, third-party widgets, markdown you don't render yourself

All three are grep-able. That's the point.

Layout & spacing

tailwind
<div class="flex items-center justify-between gap-3
            rounded-xl border border-zinc-800 p-4">
stylex
const styles = stylex.create({
  card: {
    display: 'flex',
    alignItems: 'center',
    justifyContent: 'space-between',
    gap: 12,
    borderRadius: 12,
    borderWidth: 1,
    borderStyle: 'solid',
    borderColor: '#27272a',
    padding: 16,
  },
});
  • Single-value shorthands are fine (padding: 16). The lint blocks multi-value ones (padding: '12px 16px') — longhands keep merging deterministic.
  • Prefer logical properties: paddingInline, marginBlock, borderStartStartRadius — RTL support falls out for free.
  • No scale to memorize: gap: 12 is 12px. Your design system's scale arrives as tokens instead.
Ch 4 · Cookbook

States: two idioms

tailwind
<a class="text-zinc-400 transition-colors
   hover:text-white focus-visible:text-white">Docs</a>
idiom a · conditions as values (plain elements)
link: {
  color: {
    default: '#a1a1aa',
    ':hover': '#ffffff',
    ':focus-visible': '#ffffff',
  },
  transitionProperty: 'color',
},
idiom b · render-prop states (headless components)
import { Button } from 'react-aria-components';

<Button className={({ isHovered, isPressed }) =>
  stylex.props(
    styles.base,
    isHovered && styles.hovered,
    isPressed && styles.pressed,
  ).className ?? ''
}>
  Save
</Button>
  • Note the condition lives inside the property — so states merge per property, like everything else.
  • Headless libraries normalize messy platform states (touch vs mouse, focus-visible quirks) into clean booleans — style the semantic state, not the raw selector.

Ch 4 · Cookbook

Dark mode & themes as values

tailwind
<div class="bg-white text-zinc-900
            dark:bg-zinc-950 dark:text-zinc-100">

<!-- + a .dark class toggled on <html>,
     CSS vars flipped in globals.css,
     dark: sprinkled through every component -->
stylex
// semantic tokens pick their own dark values…
export const sem = stylex.defineVars({
  bg:   { default: '#ffffff',
          '@media (prefers-color-scheme: dark)': '#09090b' },
  text: { default: '#18181b',
          '@media (prefers-color-scheme: dark)': '#f4f4f5' },
});

// …or a theme is a value, applied to any subtree
export const dark = stylex.createTheme(sem, {
  bg: '#09090b',
  text: '#f4f4f5',
});

<main {...stylex.props(userWantsDark && dark)}>
Components consume sem.bg and never know dark mode exists. Themes compose: nest them, A/B test them, theme one widget differently — no dark: in any component.
Ch 4 · Cookbook

Variants: cva was an object lookup

button.tsx · the style tables
// (a `base` create() with shared flex/radius styles is elided)

const variants = stylex.create({
  primary: {
    backgroundColor: {
      default: color.primary,
      ':hover': color.primaryHover,
    },
    color: color.onPrimary,
  },
  outline: {
    backgroundColor: { default: 'transparent' },
    borderWidth: 1, borderStyle: 'solid',
    borderColor: color.border,
  },
});

const sizes = stylex.create({
  md: { height: 36, paddingInline: 16 },
  lg: { height: 40, paddingInline: 24 },
});
…and the component
type Props = {
  variant?: keyof typeof variants;  // ← the union type is free
  size?: keyof typeof sizes;
} & Omit<React.ComponentProps<'button'>, 'className' | 'style'>;

export function Button(
  { variant = 'primary', size = 'md', ...props }: Props
) {
  return <button {...props}
    {...stylex.props(base.root, variants[variant], sizes[size])} />;
}
  • cva's whole job is now variants[variant]; defaultVariants → default parameters.
  • compoundVariants → plain booleans:
    variant === 'outline' && size === 'md' && styles.tweak
  • keyof typeof keeps props and styles in lockstep — add a variant, the union updates itself.
  • No config DSL. It's data and functions all the way down.
Ch 4 · Cookbook

Styles across component boundaries

card.tsx · precedence is decided once, here
type Props = {
  children: React.ReactNode;
  style?: stylex.StyleXStyles;        // the styling contract
};

export function Card({ children, style }: Props) {
  return (
    <div {...stylex.props(styles.root, style)}>  {/* caller wins */}
      {children}
    </div>
  );
}

// callers pass style *values*, not strings
<Card style={styles.tight} />
<Card style={onDark ? styles.inverted : styles.tight} />
  • props.style last → callers win. First → they can't override you. One decision, in one place, readable in the source.
  • Compare: cn(…, className) hopes tailwind-merge guesses your intent.
  • Forwarded styles were compiled at their definition site — passing values around is free.
  • Pair with slide 14's scoped contracts to allow only specific overrides.
Ch 4 · Cookbook

Pseudo-elements, animation, runtime values

the remaining 10% of your day
const pulse = stylex.keyframes({
  '0%':   { opacity: 0.4 },
  '100%': { opacity: 1 },
});

const styles = stylex.create({
  badge: {
    animationName: pulse,
    animationDuration: '1.2s',
    '::before': { content: '""', width: 8, height: 8 },
  },
  fullHeight: {
    height: stylex.firstThatWorks('100dvh', '100vh'),
  },
  // dynamic: real runtime values become CSS variables
  bar: (pct: number) => ({ width: `${pct}%` }),
});

<div {...stylex.props(styles.bar(progress))} />
// → class="x1exw92"  style="--x-width: 62%"
  • keyframes() returns a value you assign to animationName — scoped, reusable, no global name collisions.
  • Pseudo-elements are keys on the owner's style: '::before', '::placeholder'…
  • firstThatWorks() = ordered fallbacks, compiled into stacked declarations.
  • Dynamic styles are the sanctioned runtime hatch: the class stays static; only a CSS variable changes per render.

Ch 6 · Tradeoffs & landing

Day-one gotchas

  • 1 · margin: '8px 16px' is rejected — write longhands: marginBlock: 8, marginInline: 16.
  • 2 · You can't style children. .card:hover .icon doesn't exist — style the child directly and pass state via props. Style the owner, not the tree.
  • 3 · Token files end in .stylex.ts and may export only defineVars/defineConsts. Compiler contract, not superstition.
  • 4 · stylex.create lives at module top level with static keys — no factories, no objects built at runtime.
  • 5 · Conditionals are cond && styles.x inside props() — never assembled strings.
  • 6 · Numbers become px — except unitless properties (lineHeight, opacity, zIndex, fontWeight, flexGrow…).
  • 7 · Pseudo-element text needs nested quotes: content: '""'.
  • 8 · There is no !important. You won't need it — precedence is argument order, remember?
